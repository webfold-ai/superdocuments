# Pandoc-compatibility benchmark

How close is superdocuments' Markdown to what Pandoc 3.1.3 reads from the same file, and how close are its
formatted citations to `pandoc --citeproc`? Pandoc is the oracle and is a dependency of the benchmark only:
the library never runs it and never touches the network.

## Protocol

Readers (`score.py`, unchanged since the baseline commit; see its docstring for the exact definitions):

1. `corpus/` holds 377 inputs (`manifest.json`): LaTeX (118), DOCX (50), ODT (34), EPUB (34), HTML (42), RST (34),
   Markdown (40), BibTeX (25). Most are generated by seeded scripts (`gen_*.py`); the DOCX/ODT/EPUB files come from
   LibreOffice and Pandoc's writers; 47 files are hand-written. **The HTML, EPUB, RST and Markdown seeds are written by
   Pandoc's own writers**, which favours any reader that mimics Pandoc; the hand-written ones are listed
   separately below.
2. `oracle/<id>.json` is `pandoc -f <reader> -t json` of each input (stored; regenerate with `score.py oracle`).
3. The candidate is the converter's Markdown, read back by Pandoc with one fixed reader (`-f markdown-raw_tex`).
   Sub-scores per document: structure, features, text; fidelity is their mean. A document the converter fails on
   scores 0. "Exact" means all three sub-scores are 1.
4. BibTeX is scored apart (`score.py bib`): CSL-JSON read from each `.bib` against `pandoc -f bibtex|biblatex -t csljson`.

Citations (`cite/`): `cite_bench.py` and `cite_ts.py`, with `pandoc --citeproc` as the reference. The
formatted text of every citation and bibliography entry becomes a comparison string (italic, bold, small caps,
super/subscript marked; non-breaking and thin spaces as spaces; whitespace runs as one space; adjacent identical marks
merged); two strings are equal or they are not. Nothing else is normalised.

## Reproducing

```sh
# Readers (Pandoc 3.1.3, python3; build: cargo build --release --example sd_convert --example cite_run)
cd benches/pandoc-compat
./rescore.sh after ../../target/release/examples/sd_convert      # converts the corpus and scores it
python3 score.py report sd-before sd-after markitdown            # the table below
python3 score.py bib sd-after -- ../../target/release/examples/sd_convert --csl '{path}'
python3 disagreements.py                                         # every remaining difference, with its cause

# Citations. Third-party inputs are fetched, never committed (CSL styles: CC BY-SA 3.0; the CSL test-suite
# repository has no licence file and embeds such styles):
cd cite && ./fetch_corpora.sh          # pinned commits, sha256-checked against corpora.sha256
python3 cite_bench.py oracle           # Pandoc's reference output, development set (125 documents x 6 styles)
python3 cite_bench.py run csl ../../../target/release/examples/cite_run && python3 cite_bench.py report csl
python3 cite_bench.py run bib ../../../target/release/examples/cite_run && python3 cite_bench.py report bib
CITE_SET=heldout python3 cite_bench.py gen && CITE_SET=heldout python3 cite_bench.py oracle      # held-out set
CITE_SET=heldout python3 cite_bench.py run csl .../cite_run && CITE_SET=heldout python3 cite_bench.py report csl
CITE_PANDOC_NAMES=1 CITE_SET=heldout python3 cite_bench.py run csl .../cite_run   # see "Pandoc names" below
python3 cite_ts.py gen suite-src && python3 cite_ts.py oracle && python3 cite_ts.py run .../cite_run && python3 cite_ts.py report
python3 cite_bench.py golden           # (re)writes the golden files the Rust tests use
```

`cargo test --release --test pandoc_compat_golden` runs without Pandoc and without the fetched inputs.
`results/` holds our own pass/fail tables (`cite-*.csv`, one row per document and style) and the per-document reader
scores (`sd-before.json` is origin/main at 3e66b36, `sd-after.json` this branch, `markitdown.json` MarkItDown 0.1.9 with
`[docx,pptx,xlsx]`, run by `run_markitdown.py`).

## Results: readers (fidelity, mean of structure/features/text; exact documents in brackets)

| Format (n) | superdocuments before | after | MarkItDown 0.1.9 |
|---|---|---|---|
| DOCX (50) | 0.934 (9) | 0.972 (34) | 0.924 (8) |
| EPUB (34) | 0.804 (0) | 0.985 (0) | 0.831 (0) |
| HTML (42) | 0.834 (3) | 0.990 (36) | 0.968 (3) |
| LaTeX (118) | 0.857 (2) | 0.968 (10) | 0.428 (0) |
| Markdown (40) | 1.000 (40) | 1.000 (40) | 1.000 (40) |
| ODT (34) | 0.548 (0) | 0.948 (3) | 0.000 (34 failed: unsupported) |
| RST (34) | 0.000 (34 failed: unsupported) | 0.996 (17) | 0.769 (0) |
| All scored (352) | 0.764 | 0.977 | 0.658 |

Generated versus hand-written (after): DOCX 0.965 / 0.998; HTML 1.000 / 0.966; LaTeX 0.978 / 0.779 (six
documents, two of them with an appended reference list, see cause L2); RST 0.999 / 0.990. The HTML and RST generated
rows are Pandoc-writer output read by a reader tuned on the same corpus: read them as an upper bound.
"Before" is the first measured state, a clean build of origin/main at 3e66b36 scored against this corpus
(the corpus was revised after the first baseline commit, so the baseline was re-measured, not copied).

BibTeX to CSL-JSON against Pandoc (25 files, 179 entries): exact entries 0 of 179 before, 179 of 179 after (field F1
0.648 to 1.000). The conversion is tuned to this corpus; entry types and fields it does not contain are not tested.

## Results: citations (exact matches with `pandoc --citeproc`)

| Set | Documents x styles | Citations | Bibliography entries |
|---|---|---|---|
| Development (csl track) | 125 x 6: APA, Chicago author-date, IEEE, Harvard (Cite Them Right), Nature, MLA | 7454 / 7458 (99.9%) | 4362 / 4362 (100%) |
| Development (bib track: our BibTeX reader too) | same | 7454 / 7458 | 4362 / 4362 |
| Held-out, first run before any fix | 125 x 4: Vancouver (Elsevier), AMA, Springer basic author-date, ASA | 4929 / 5080 (97.0%) | 1923 / 2952 (65.1%) |
| Held-out, after fixing what it showed | same | 5079 / 5080 (100.0%) | 2214 / 2952 (75.0%) |
| Held-out, `--pandoc-names` | same | 5079 / 5080 | 2952 / 2952 (100%) |
| CSL test suite as documents (stress) | 845 tests, each with its own style | 877 / 1279 (68.6%) | 416 / 575 (72.3%) |

- The development set is what the processor was developed against, so its numbers are not an estimate of
  general agreement. The held-out set uses other documents (another seed) and four styles that were not looked at
  before the first run; the first-run row is the honest estimate, the second row is after fixing the defects it showed.
- Pandoc names: when `<names>` has no `<name>` child, Pandoc ignores the name options set on `style`, `citation` or
  `bibliography`; citeproc-js and the style's intent (AMA relies on it for "Rossum G van") apply them. We follow the
  latter by default; `Processor::with_pandoc_names(true)` (`cite_run --pandoc-names`) follows Pandoc, and then the
  AMA bibliography matches 738 of 738. The one held-out citation and the four development citations still different
  are in `DISAGREEMENTS.md`.
- The stress corpus is the CSL project's citeproc test suite at 6eefc5b (845 `processor-tests/humans` fixtures),
  turned into documents and compared with Pandoc, not with the suite's expected results. 529 of 845 tests match
  completely (62.6%). It is a set of edge cases (locales, name particles, disambiguation, text case, ...), so low rates
  are expected; 316 tests differ and are not classified one by one (`results/cite-suite.csv` has the per-test table).
- Golden tests (`tests/pandoc_compat_golden.rs`) use three small styles written for this repository
  (`cite/golden-styles/`) on all 125 development documents: 375 document/style pairs, all equal to Pandoc's stored output.
  The reader goldens (`golden/<id>.md`) are superdocuments' own Markdown as scored, not Pandoc's.

## Deviations from the protocol

- No README existed at the baseline commit; this file is it.
- `rescore.sh`, `disagreements.py` and everything under `cite/` are new; `score.py` is unchanged and the baseline and
  MarkItDown were re-scored with it on the final corpus.
- The citation oracle is Pandoc 3.1.3's `--citeproc` on this machine; the CSL styles and the test suite are fetched at
  the pinned commits in `cite/fetch_corpora.sh` and are not part of the repository.
- GitHub has no CI runner attached to this repository; none of these numbers was produced by CI.
